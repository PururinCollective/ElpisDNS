Pick your size

The same binary runs everywhere. What changes is how much memory you give its cache, and what it runs on.

Home lab

For a household, a flat full of gadgets, or a tinkerer's rack.

Runs on
Raspberry Pi 4 or 5, an old mini PC or NAS, or an LXC container
CPU
Any 64-bit ARM or x86, 1–2 cores
Memory
1–2 GB — a 171–410 MiB cache, about 340,000–830,000 names
Disk
A few MB. The static binary is about 1.4 MB
VM or container
Fine

Put AdGuard Home or Pi-hole on the same box and point it at 127.0.0.1:5335.

VM & small business

For an office, a school, a campus network or a VPS.

Runs on
A KVM or Proxmox VM, or an LXC container — one per instance, each with its own IPv6 address
CPU
2–4 vCPU; x86-64-v3 (AVX2) or newer is ideal
Memory
4 GB — an 819 MiB cache, about 1.6 million names
How many
Two, so one can restart while the other answers
VM or container
Recommended

A container per resolver is easy to firewall, easy to move, and easy to spot in a packet capture.

ISP & operator

For thousands of subscribers, where every millisecond is felt.

Runs on
Dedicated servers — real hardware, not virtual machines
CPU
8+ physical cores, x86-64-v3 (AVX2) or newer, or Arm Neoverse
Memory
32–64 GB ECC; the cache grows itself up to 16 GiB
Network
10 GbE with multiple receive queues (RSS)
How many
Two or more per site, behind anycast or a load balancer
VM or container
Not at this scale

Why real hardware? · Commercial support is available.

Why real hardware for ISPs?

Virtual machines are great right up until thousands of people share one resolver. At that point steady beats fast, and a hypervisor gets in the way of steady.

Every core counts

Elpis runs one worker per CPU core, each with its own socket. Real cores and real NIC queues let it scale straight up.

No noisy neighbours

A VM shares its CPU. When the host gets busy, the stolen time shows up as random delays your subscribers can feel.

One hop fewer

Packets reach the resolver without a virtual switch in the way, so latency stays low and flat under load.

Memory that stays put

A big cache is what makes answers instant. Dedicated RAM is never ballooned away or swapped out by a host.

For scale: on an eight-core VM, answers from cache measure 600,000–780,000 queries a second, about 200,000 on a single thread, with a 0.6 ms median. Dedicated hardware gives you that headroom without the jitter.

Install in five steps

Linux shown here. The BSDs and macOS work too — see the compiling guide.

Get it

Download the static binary from Releases — it runs on any recent Linux with nothing else to install: 

sudo mkdir -p /opt/elpis-resolver/bin
sudo cp elpis elpis.conf /opt/elpis-resolver/bin/
/opt/elpis-resolver/bin/elpis -t        # check the config and exit

Or build it yourself. A C compiler and make are all it needs:

sudo apt install build-essential git
git clone https://github.com/PururinCollective/elpis-resolver.git
cd elpis-resolver && make
sudo make install                        # to /opt/elpis-resolver/bin

Configure it

With no changes at all, Elpis is a working resolver on 127.0.0.1:5335 — perfect when AdGuard Home runs on the same machine. To serve a network, edit /opt/elpis-resolver/bin/elpis.conf: 

listen: [2001:db8::53]@53
listen: 192.0.2.53@53
access-control: 2001:db8::/48 allow
access-control: 192.0.2.0/24 allow
dnssec: yes

Swap in your own addresses. Anything not allowed is refused, so an open resolver never happens by accident. Every other setting is documented in the file at its default.

Run it as a service

The systemd unit binds port 53 without running as root. It needs an account to drop to: 

sudo useradd --system --user-group --no-create-home --shell /usr/sbin/nologin elpis
sudo install -m0644 contrib/elpis.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now elpis
Starting it stops systemd-resolved, so the two never fight over port 53. Point /etc/resolv.conf at Elpis afterwards, or remove the Conflicts= line if you keep resolved and run Elpis on another port.

Point your filter at it

In AdGuard Home, open Settings → DNS settings → Upstream DNS servers and replace what's there with your resolver: 

127.0.0.1:5335
[2001:db8::53]:53

Running two? List both, and set Upstream mode to Load-balancing. In Pi-hole, the same goes in Custom DNS servers as 127.0.0.1#5335.

Check it

Ask it for a name, then ask it what it is. The second line answers with its version, build, CPU kernel and whether DNSSEC is validating. 

dig @127.0.0.1 -p 5335 example.com +dnssec
dig @127.0.0.1 -p 5335 elpis.sakurako.oomuro TXT

Want graphs? Add webgui: yes and a password for a read-only status page on loopback — reach it over SSH or a VPN.

Tuning for your CPU

The default build runs on any CPU of its kind, and still picks AVX2 at start-up when it's there. For the last few percent, build for the exact processor it will run on. 

make static OPT="-O3 -fno-strict-aliasing -march=x86-64-v3"
x86-64-v3
Intel Haswell (2013) and later, AMD Zen and later
znver4
AMD Zen 4: Ryzen 7000, EPYC Genoa
neoverse-n1
Ampere Altra, AWS Graviton2 (use -mcpu on ARM)
cortex-a76
Raspberry Pi 5

One thing to watch

A binary built for a newer CPU stops with Illegal instruction on an older one. For a mixed fleet, pick the lowest x86-64-vN level they all support.

The first log line always tells you what you're running: compiler, CPU target and the SIMD kernel in use.
